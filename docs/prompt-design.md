# Prompt 系统设计与维护

本说明供维护本库的人或 Agent 理解当前职责、设计依据与验证边界，不是业务开发时每次必读的运行指令。2026-09-16 的重构已随合并提交 `15f5173` 进入主线；历史变更见提交记录，本文维护当前约定。

## 原则

Prompt 和 skill 提供模型无法自行确定的项目事实、个人取舍、真实流程依赖、工具用法和验收要求，不重复一整套软件工程课程。任务表达清楚目标、上下文、约束和验收；已有信息引用即可。

硬约束、用户偏好、授权要求、项目事实与针对模型的临时补丁应能区分。行为要求是否仍成立，与实现它的某段 Prompt 是否仍必要，是两件事。精简措辞不自动取消用户取舍、授权边界或真实性要求；不因一次失败就永久增加全局步骤。

## 阶段与工作偏好

前期想充分，开发有边界。Grill Me 用于深入发现模糊和遗漏，不以能写出最小版本为提前结束标准。未来需求可以影响方案讨论，但讨论范围不等于本期实现范围。

文档承接共同理解，不把未决内容补成确认结论。开发使用已确认文档或对话中的当前交付目标，不沿用访谈的逐题等待方式。简单任务不因此增加访谈、文档或审批步骤。

多步开发优先采用曳光弹式迭代，以适合任务的可验证结果推进；产品功能、库、迁移和调查可以有不同产物。这是开发偏好，不是要求所有任务补齐前后端，更不是缩短前期访谈的理由。可执行规则见 [AGENTS.md](../AGENTS.md)。

## 规则归属

| 维护位置 | 职责 |
| --- | --- |
| 用户级 `AGENTS.md` | 跨任务协作、文档交接、开发中新信息处理、权限与安全底线 |
| 项目及模块 `AGENTS.md` | 已核实的入口、命令、契约、局部取舍，包括项目实际的凭据来源与外部影响 |
| `grilling` | 访谈方式、充分探索、退出和交接，不管理退出后的开发 |
| `deliver` | 当前结果的实现、整合、验证和交付 |
| `to-spec` / `handoff` | 分别保存本次规格与跨会话任务状态，不替代长期项目知识 |
| `code-review` | 审查具体变更的需求、正确性与回归，复核证据并合并发现 |
| `to-tickets` | 任务粒度、真实依赖、验收与记录方式 |
| `project-context` | 核实并维护已确认的项目指令、领域知识和重要决定，不替用户制定新规则 |
| 两份设计技能 | 分别形成方案与检查方案，不规定固定的实现形态 |
| 维护说明、示例和测试 | 解释与检验规则，不独立增加运行要求 |

以明确的维护位置避免同一决策出现不一致的规范。允许技能为其特定产物保留必要的简短提示，也允许说明文档和测试复述预期行为；不是要求消除所有语义重复。修改时核对相关用例，不能把少量重复本身判为设计缺陷。

开发中新信息的分类与授权边界以全局约定为准；`deliver` 和 `to-tickets` 只补充结论变化后如何更新产物。访谈中的文档记录是已有授权下的动作，不代表切换阶段。

## 管辖范围与外部依赖

本库维护自己的 `AGENTS.md`、`skills/` 及安装器登记的目标副本，不代表宿主加载的全部指令面。项目局部目录、自定义目录、上游技能、preset 或运行时 provider 都可能提供其他内容。未登记不等于无用，也不代表已获授权删除；`AGENTS.md` 不承担复制全部技能目录的职责。

实际支持与验证目标为用户使用的 Codex 和 DSH 组合。模型与宿主分别记录版本；共享行为变更覆盖这两套目标环境，宿主专属适配重点验证该宿主及相关兼容性，不以固定模型数量作为退役门槛。Claude Code frontmatter 兼容不等于已完成该宿主的集成验证。

修改安装面前保存本次测试涉及作用域的有效配置，检查实际解析来源、同名覆盖与加载记录。外部入口可能调用自维护版本；从需要保留的入口沿有向依赖验证，不按无向连通组或来源批量禁用。没有悬空引用只能证明结构连通，不能证明新旧实现行为兼容。快照和证据的最小记录见 [实验记录约定](../evals/records/README.md)。

## 安全取舍与验证

安全部分只在 `AGENTS.md` 维护运行规则；这里记录设计意图。目标不是固定选择某种凭据存储，而是在实际环境中平衡风险、潜在损失与实施、维护、验证、恢复成本。文件、环境变量、系统钥匙串或专用服务都可能在不同环境中合理；更复杂不自动等于更适合，也不能因为本地运行就省略风险判断。

可验证性是选型成本的一部分。采用的方案应让存储、读取和实际使用是否成功能够被确认，并让失败可见；但“容易查看”本身也不等于安全或功能验证已经完成。项目需要记录实际采用的凭据来源、环境前提和交付时真正走的加载路径。

验证结论按证据范围表达。写入返回值只能证明写入调用返回，文件存在只能证明文件存在，签名成功只能证明所用凭据能够签名；这些都不能自动推出交付后的凭据加载、请求执行或最终业务结果已经成立。资金功能的端到端门槛覆盖实际凭据加载、签名或鉴权、请求执行及预期业务结果，同时受环境和真实操作授权约束。模拟、测试环境和真实环境分别报告，不为完成验证擅自扩大资金操作授权。

## 技能与调用策略

调用方向为 `grill-me → grilling`；`grill-with-docs → grilling / project-context`。`grilling` 不反向调用入口，记录术语不需要重新开启一轮访谈。

六个显式入口为 `grill-me`、`grill-with-docs`、`implement`、`to-tickets`、`to-spec`、`handoff`；它们同时提供 Codex YAML 与 DSH/Claude Code 识别的 frontmatter，详见 [调用策略](../README.md#使用与调用策略)。普通工作不因为需要规划就自动调用显式入口。DSH 会在模型侧加载时检查策略，因此更改标记还需检验保留入口的依赖，不能通过绕过加载策略维持旧流程。

`software-design` 形成或调整方案，交付推荐方案、依据和必要边界；`design-review` 检查已有方案，交付有证据的问题与结论。保留这些结果标准，但去掉旧版的单向抽象门槛、固定概念分类和理论必读流程。增加和减少抽象都依据实际成本判断，不新增共享理论层，也不把切换技能等同于独立审查。

迁移计划区分最终状态与过渡状态；设计、拆分与评审对兼容、事实归属、验证和退出条件使用一致标准。临时适配本身不是缺陷，不能安全共存时才要求协调修改。

### 项目上下文维护

`project-context` 合并原 `domain-modeling` 的领域澄清与记录职责，吸收项目指令模板能力，不另建 `project-instructions`。统一维护入口，不合并所有输出：项目 `AGENTS.md` 保存工作入口、命令和已确认约束；领域文档保存术语及业务语义；ADR 或设计记录保存重要选择的背景与状态。已有项目布局优先，不要求创建所有文件。

保留术语冲突检查、边界场景检验和代码/文档交叉核对。实现现状、预期行为和已接受决定可能不同，不能通过覆盖一方伪造一致，也不能把一次选择升级为永久规则。新增业务或架构取舍交回当前任务，维护技能只在已有授权内更新相关知识。

调用可以来自用户的维护请求，也可以来自已授权任务中的相关同步。`grill-with-docs` 只交接本次确认的术语与必要决定，不自动授权维护项目指令；project-context 不反向调用访谈入口。普通查阅不启动写入，文档维护不成为每次开发后的强制步骤。

原来的三个来源——项目指令示例、领域上下文格式、ADR 格式——统一放入该技能的 `references/`，由本次维护产物按需选择。它们不是三份必填模板；小项目可能只需更新已有文件中的一段话。`project-conventions` 仍提供个人工具链默认值，项目上下文记录的是实际采用的方案。

### 名称兼容的范围

`design-before-coding → software-design` 不留误导时序的旧入口；`domain-modeling → project-context` 合并后也不留重复入口，相关调用同步更新。`implement → deliver` 保留为用户显式调用的兼容入口，不承诺模型隐式调用兼容；这不是“所有包装必须删除”的通用标准。

旧名是否从安装环境清除，受 manifest 与目标目录范围限制，见 [安装与更名说明](../README.md#技能替换与清理)。不推定用户本机已安装了哪份配置。

## 选择性移植

`to-spec`、`handoff` 和 `code-review` 改编自 [mattpocock/skills](https://github.com/mattpocock/skills/tree/c55ee46073ed923f86ce59a5eb3b6d895095d1b7)，以该提交固定来源；各技能的 `metadata.upstream` 指向具体原文件。这不是同步上游整套工作流，更新需审阅本地取舍。

`to-spec` 合成已有讨论，产物是当前规格；保留范围、行为和验收要求，删除上游的测试边界固定数量／额外确认、长用户故事要求、setup 依赖和自动 tracker 发布。未决问题保持未决，整理文档不自动授权实现。

`handoff` 保存任务进度、证据与接手入口，区别于 `project-context` 的长期知识。保留引用和脱敏，改为按下一执行者可访问性选择位置，不固定系统临时目录；可选技能建议不构成加载命令或新的操作授权。

`code-review` 保留固定审查范围、需求与项目标准的双重核对，补齐工作区状态、行为缺陷、回归及证据复核；不固定双代理、代码异味清单或两轴不可合并。它和 `design-review` 按具体变更／专项结构审查区分，不默认互相触发。是否运行检查取决于实际授权，审查不自动批准、修改或发布。

三个技能均不加载上游 setup、tracker 或工作流入口，已有技能也不新增对它们的强制依赖。`to-spec` 与 `handoff` 是显式入口；`code-review` 可按已要求的评审任务选择。相关模板只在需要产物结构时读取，不让所有开发默认经历规格—交接—评审流水线。

已安装的同名上游技能可能被目标目录内的本地版本备份替换，但其他作用域不会自动消失；其清理需核对来源及本地改动。其余上游能力可按实际需求选择，不为“以后可能用到”要求常驻，也不把这次移植视为批量卸载授权。新技能的成对场景见 [移植技能回归](../evals/ported-skills.md)，当前未运行模型行为实验。

## 安装与辅助技能

`git-commit` 采用项目已有规范优先、个人格式作为默认值。`video-summary` 提供工具知识，在已有授权内保持探测与下载认证参数一致，不强制读取登录态。

资金与凭据规则改为“选型按实际风险和成本权衡，验证按实际交付路径给证据”。这不是降低资金执行的端到端门槛，而是避免把复杂机制本身当作安全或成功的证明；全局规则仍要求资金功能正式启用前完成授权范围内的可验证端到端测试。

安装器采用独立目录复制，拒绝符号链接形式的目标 `skills/` 根目录，只依据 manifest 清理过期技能。契约由文档和自动测试记录；安装器不接管外部技能或其他宿主配置。

`project-conventions` 提供语言工具链默认值，NCM 技能提供专项转换能力；它们不成为所有任务的前置流程。领域知识维护及其格式归 `project-context`。

## 资料消费者与维护

本文件用于维护本库时理解设计依据。`evals/prompt-behavior.md` 由受委托的评估者或 Agent 读取，选择适用案例、在隔离环境中比较配置并保存执行证据；它是规格，不是可直接执行的 runner。修改行为规则时，先选取或补充对应失败案例，条件允许时进行真实对照，不能运行时明确标注。纯名称或链接调整不因此变成完整行为评估工程。

项目模板只保留在 `project-context/references/`，随技能安装并由技能消费；删除独立 `task-brief` 教程，其有用场景已由回归规格覆盖。普通业务任务不额外读取本库维护资料，也不把评测预期注入被测会话。

## 验证与后续维护

[安装契约测试](../tests/test_install_contract.py) 检查可确定的脚本行为；[行为回归规格](../evals/prompt-behavior.md) 仍需在实际使用的 Codex 与 DSH 配置中运行。两类验证分开报告，不把文本、语法或脚本测试当作模型行为改善的证据。

模型升级或调整规则时，按实际支持范围比较同快照配置。访谈看模糊消除和遗漏发现，文档看忠实记录，开发同时检查授权内推进与必要暂停。针对某组额外措辞可做消融，但删除一处后无差异，不证明模型已经内化；同样的要求可能仍在其他上下文中。

只为正在调整的行为组保留 [轻量记录](../evals/records/README.md)，不为全部 bullet 建台账，也不将记录注入运行指令。通过、失败、未运行、无法判断及“未观察到差异”都应有准确记录；实验结论与保留/精简/待复验的决定分开。没有实际实验时不能声称规则有效或已冗余。

## 配置依据

- [Codex skills](https://developers.openai.com/codex/skills)：`agents/openai.yaml` 中的 `policy.allow_implicit_invocation` 控制隐式调用，不是权限隔离。
- [Claude Code skills](https://code.claude.com/docs/en/skills)：`SKILL.md` frontmatter 中的 `disable-model-invocation` 控制该宿主的自动调用。
- [DSH 技能加载源码](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45fbc7f8e46dd73185e68295696d1297887/packages/skill/tool-skill/src/index.ts)：该版本分别检查用户显式调用与模型加载，后者校验 `isModelInvocable`。这是固定版本的实现依据，不是用户本机版本的实测报告。
