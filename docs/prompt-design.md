# Prompt 系统设计与本次取舍

基线：`yim7/agents`，提交 `695f8add8dd31827ecc874ade2c64d9ba9b539f1`。
本文供维护者审阅，不是 Agent 每次需要加载的运行指令。

## 原则

Prompt 和 skill 应提供信息增量：模型无法自行确定的项目事实、个人取舍、真实流程依赖、工具用法和验收要求。不重复通用工程口号，不为旧模型的每次失败永久增加一条全局命令。

任务表达清楚目标、上下文、约束和验收。清晰不等于冗长，已有信息引用即可，普通技术判断留给模型。硬约束、默认偏好和暂时的模型补丁应能区分；选择某种方法是有效取舍，不代表要重新规定该方法的全部步骤。

减少的是对实现形态的预设，不是自主执行责任或验证质量。TDD、类、函数、DTO、局部重构和代码复用都由具体任务决定；用户明确选择的方法在其范围内执行。

## 统一概念与工作偏好

统一使用“当前交付目标”：本轮要交出的可验收结果。它不是新术语体系、必填文档或审批节点；“切片”仅是可选的任务拆分方法。

保留“可用版本优先，快速迭代”的取舍。多步开发优先采用曳光弹式迭代，尽早验证真实路径，再依据运行结果和用户反馈完善；不先穷尽全部设计才开始验证，也不把未经验证的演示宣布为整体完成。库、迁移和调查有各自的验证产物，无需凭空补齐前后端。

访谈的逐题形式只在访谈阶段生效。信息足够或用户切换阶段就退出，保留结论而不延续等待方式。已有实现授权时连续推进；只要求文档时不擅自开发。

执行中新增信息分开处理：影响当前结果的事实及时修正，明确的范围变更更新安排，未来设想与可选改进留到后续。新信息不自动增加当前验收门槛，也不自动重启访谈。

## 信息放在哪里

| 位置 | 保存什么 | 不保存什么 |
| --- | --- | --- |
| 用户级 AGENTS.md | 协作方式、交付偏好、授权边界 | 每个项目都执行的设计步骤 |
| 项目及模块 AGENTS.md | 真实入口、命令、兼容与状态约束、局部取舍 | 未核实的假设、重复全局口号 |
| SKILL.md | 适用场景、必要知识或流程、预期产物与退出条件 | 无条件的软件工程课程 |
| 当前任务 | 本次目标、上下文、限制、授权、验收 | 已知信息的重复和假想未来需求 |
| 维护文档与回归案例 | 指令的依据、例外和效果记录 | 每次编码必读的额外关卡 |

同一规则有明确的维护位置。全局保留跨任务原则，技能只补充场景细节，不复制多套稍有不同的标准。安装脚本保持不变；软件设计技能改用按职责命名的入口，不保留旧名兼容包装。

## 技能调整

`grilling` 负责澄清与退出，不要求问尽所有未来问题；`grill-me` 和 `grill-with-docs` 只是入口。两个入口使用 `agents/openai.yaml` 的显式调用策略，不依赖 frontmatter 标记来实现 Codex 调用控制。

`deliver` 负责当前目标的连续推进、必要协作、整合与交付。`to-tickets` 仅在确实需要拆分时记录交付目标、验收与阻塞依赖。它们保留曳光弹式偏好，不强制固定的拆分粒度、代理数量或审批步骤。

`software-design` 负责形成或调整当前软件问题的设计方案，交付推荐方案、取舍依据和必要边界，不限定在编码前使用。只要求设计时不直接修改实现；已有实现授权时，结论足以支持当前工作后继续原任务。去掉单向抽象举证顺序、固定概念分类和理论必读流程，保留与改变现状使用同样的成本判断。

`design-review` 检查已有方案、规格、迁移计划或实现，交付有证据的问题与检查结论，不自动重写方案。它基于已确认约束、具体证据和可解释的风险判断，不从审查者想象的最佳设计推导项目硬约束。与 `to-tickets` 一致区分最终状态与过渡状态，允许有兼容、验证和退出条件的分批迁移。

两者按主要产物划分，而非按思考动作或开发阶段划分：设计中可以检查风险，评审中可以给出修复方向。它们可独立使用，不构成默认的设计—评审—修改循环；同时要求审查和修订时按原授权连续交付，不新增确认步骤。不新增公共设计规则技能，也不把切换技能等同于独立审查。

`git-commit` 先沿用项目已有规范，再使用英文 Conventional Commits 默认值。`video-summary` 保留具体工具知识，去掉强制读取浏览器登录态的顺序，沿已有授权使用并传递认证参数。

`project-conventions` 及 Python 约定、`domain-modeling` 及格式、`implement` 兼容入口、`ncm-converter` 及脚本不改。八份旧设计参考文件原样移到 `docs/archive/`，不再从运行技能引用，也不随 skills 安装。

## 维护与验收

这次不新增“每次都检查是否巨类”的反向禁令，不固定类型数、代码行数、测试数或代理数。重点是规则对结果是否有收益，而不是文本是否更短。

待运行的回归场景包括：GrillMe → 文档或实现的阶段切换；执行中分别出现未来设想、当前约束和明确范围变更；小任务；指定 TDD；合理迁移；设计复审；同一模块连续几次增量需求。具体见 [试用与回归](prompt-evaluation.md)。

静态检查与文件一致性检查不能证明模型行为改善。模型升级或新增规则后，基于相同项目快照比较必要上下文基线、旧配置和新配置。记录无意义等待、未授权范围扩张、首次可验证结果、正确性、维护成本和执行成本；不以少问问题或更快产出掩盖必要澄清和质量下降。

失败先保存为案例。规则有稳定收益才保留；只适用于一个模块就下移；旧模型补丁不再有效就删除。测试记录和维护说明不自动成为运行指令。
