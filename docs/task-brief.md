# 任务描述参考

这是供人组织任务的参考，不是要求每次填满的表。已在对话或仓库中明确的信息用引用即可；未知的实现细节交给 Agent 核查和决定。

```text
当前交付目标：这次交出什么可验收的结果。
上下文：相关入口、现状、决定、文档或问题证据。
约束：必须保持什么，这次不做什么，已经授权到哪里。
验收：通过什么可观察结果判断完成。

方法约定：需要改变默认做法或方法本身是要求时才写，例如本次用 TDD。
```

## 开发任务示例

以下是虚构的 SQL cell 任务，不声称仓库已经存在这些接口：

```text
给 SQL cell 增加超时和主动取消能力。

先核对当前执行入口、状态管理和后端适配方式，沿用已有接口约定。
取消单个 cell 不得误取消其他 cell；本次不引入跨进程调度系统。
允许为这项能力做相关的职责调整，不扩展到其他功能。

完成后能验证正常结束、超时、主动取消，以及取消与完成并发时的结果；
资源应被释放，不能仅更新界面状态就声称执行已停止。
交付实际运行的验证和未覆盖部分。不部署。
```

默认开发偏好已经在全局约定，不必每次重复曳光弹的理论或步骤。大任务可先明确最近的可验收结果，再在授权内继续；这不要求在前期访谈中提早停止探索。

## 前期访谈、落文档与开发示例

需要充分澄清时：

```text
使用 $grill-me，帮我全面梳理文件导入的需求、假设与边界。
暂不实现。以后可能支持 Excel，也讨论它对当前方案有什么影响；
讨论到的未来需求不代表本次全部要做。
```

形成共同理解后：

```text
结束访谈，先整理 Spec，不开发。
区分已确认决定、本次 CSV 范围、后续 Excel 需求和未决问题。
```

授权开发时：

```text
按 Spec 完成本期 CSV 上传与前 100 行预览，并验证结果。
沿用文档中的约束，Excel 留后续，不部署。
```

同一句“以后支持 Excel”，在访谈中可以用于检验方案与探索取舍，在开发中不自动扩大当前实现。开发时补充“当前文件有数 GB”属于需要核查的当前事实；“这版必须支持 Excel”属于明确范围变更。不要把三者都处理成重新开展完整访谈，也不要以范围已定拒绝修正错误。

这些阶段按用户选择使用，不是每个任务的必经流程。已有授权允许直接转入实现时，无需再索要同范围确认。

## 简单任务示例

```text
把设置页按钮“保存配置”改成“保存”。不改变行为，沿用现有文案语言和组件。
```

不需要附上通用设计准则，也不需要为了凑四个字段而重复仓库信息。
