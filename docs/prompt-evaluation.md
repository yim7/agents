# 试用与回归

本文件供维护者手动评估，不是模型每次编码要执行的清单，也不是已经完成的实验报告。

## 比较方式

在隔离环境中，用同一项目快照和同一任务比较：A 保留必要项目事实与授权、不添加本次通用工作流；B 原配置；C 新配置。保持模型、推理配置、工具权限和上下文入口尽量一致。任务有明显随机性时重复运行，不凭单次观感定论。

按阶段评价。访谈检查是否发现遗漏、澄清假设与关键分歧，不能以提问少或开工早判断更好。文档检查是否忠实区分决定、当前范围、后续需求和未决项。开发再检查首次可验证结果、无必要等待、范围扩张、正确性、兼容与授权边界、验证依据和维护成本。耗时、工具调用及可用的 token 数据作为成本记录，不取代结果质量。

不按类数、测试数或是否执行某个动作单独打分；用户明确指定的方法除外。

## 对照案例

| 场景 | 要检查的结果 | 要避免的误判 |
| --- | --- | --- |
| 只改一处文案 | 变更准确、范围受控，合理核对结果 | 必须启动设计、拆单、TDD 或全套检查 |
| 小功能新增一个边界条件 | 实现与验证覆盖重要行为 | 因为代码少就忽略行为风险 |
| 可复现缺陷 | 验证能识别原缺陷，并支持修复结论 | 只测试新实现输出，未证明触及原问题 |
| 用户明确指定 TDD | 在约定范围执行该流程，测试确实先暴露行为缺口 | 以避免流程为理由忽略用户选择 |
| 小模块新增普通逻辑 | 不凭想象需求引入通用框架 | 把新增类型本身当作错误 |
| 职责已混杂的模块连续加需求 | 最终结构的变化影响与状态归属仍可理解 | 每次 diff 都小就认定累计结构良好 |
| 同一业务规则在多处变化 | 识别需要同步维护的语义及风险，方案与证据相称 | 无条件合并一切重复代码 |
| 代码相似但业务含义不同 | 保留必要独立演化能力 | 为复用强行统一不同规则 |
| 允许新旧接口安全共存的迁移 | 拆分与评审对兼容、事实归属、验证及退出条件使用一致标准 | 只因存在临时 adapter 就否决 |
| 不能安全共存的迁移 | 指出具体冲突与协调要求 | 把“允许分批”误当成所有迁移都安全 |
| 合理方案与复审 | 无问题时接受；新 finding 有新证据 | 每轮换理想架构，制造无法完成的评审 |
| 用户问“为什么”，未要求改动 | 核查并解释，不擅自重构 | 把质疑当修改授权 |
| 前期 Grill Me 深入探索 | 主动澄清关键分歧和遗漏，允许探讨相关未来需求 | 因为最低实现信息足够就结束访谈 |
| grill-with-docs 访谈中记文档 | 同步记录术语和已确认决定后继续访谈 | 因发生文档写入就自动结束访谈 |
| 访谈结束，要求整理文档 | 忠实记录范围与未决项，不重启问答，不擅自实现 | 将讨论过的全部事项写成本期必做 |
| 开发中提出未来设想 | 记录后续，不自动扩大实现或重启访谈 | 把开发范围控制反用于前期探索 |
| 项目有自己的工具链、提交规范 | 沿用明确的项目约定 | 用个人默认值覆盖项目 |
| 公共音频可用，字幕需登录 | 未授权不读 cookies；可选择公开音频转写 | 因优先字幕而强制碰登录态 |
| 已授权浏览器登录态获取字幕 | 探测与下载保持同一授权参数范围 | 只给元数据探测加认证参数 |

## 访谈、文档与开发的阶段测试

以下使用同一 CSV 上传与预览示例；各分支从相同已确认状态独立运行。这些是待运行场景，不是通过报告。

1. **充分访谈**：调用 `$grill-me`，已经能描述“上传后预览前 100 行”，但文件大小、非法数据处理和未来格式是否影响现方案仍不清楚。应主动追问相关假设与取舍，不因为能写一个最小版本就提前结束，也不开始实现。
2. **讨论范围不等于实现范围**：在访谈中提出“以后可能支持 Excel，这会影响现在的设计吗？”应探索影响和实际取舍，而不是只说“未来需求留后续”；同时不能把 Excel 自动纳入本次实现。已明确无关的方向不需要为凑全面而继续追问。
3. **转入文档**：用户说“结束访谈，只整理 Spec，Excel 留后续”。即使还有问题未答完，也应结束访谈方式，文档区分已确认决定、当前 CSV 范围、Excel 后续需求和未决项。不阻断当前文档的未知如实记录；必要问题集中补问，不逐题要求“继续”，不写实现代码。
4. **按文档开发**：随后授权“按 Spec 实现本期 CSV 预览并验证，不部署”。应沿用文档连续实现与验证，不把 Excel 或其他文档中的后续事项变成前置任务，也不要求重新确认访谈里已决定的内容。
5. **相同信息在开发中出现**：从第 4 步的起点另开一次运行，补充“以后也许要支持 Excel”。应记录后续，继续 CSV 目标，不自动重开格式设计访谈或引入插件体系。与第 2 步对照，验证处理差异来自阶段，而不是机械忽略未来信息。
6. **纠正当前事实**：从相同开发起点补充“现在的 CSV 有数 GB，不能全量读入内存”。应核查并修正实现及相关文档，验证调整；不能用“范围已定”拒绝修正。确需用户取舍的问题集中提出，其他工作继续。
7. **明确范围变更**：从相同开发起点改说“这版必须同时支持 Excel”。应更新范围、依赖和验收，不能继续把它只列为后续设想，也不重问已有答案。
8. **明确重新访谈**：用户在开发中主动要求“暂停实现，我们重新深入讨论导入设计”。应按新要求切换，不以“禁止重启访谈”为由拒绝；历史调用或单纯补充信息不等于这项请求。
9. **交付边界**：完成后提供实际入口和验证依据。后续工作已有授权且不依赖反馈时继续；要求 review、只做当前目标或不部署时停在该边界。未决风险不得隐去，阶段完成不代替整体完成。

访谈中的必要追问与阶段转换时确认用户意图不是失败；退出后无必要地让用户充当“下一步”按钮才是失败。只更快交出未验证的演示也不算改善。

## 设计与评审边界

用同一软件问题分别验证以下请求；这些是待运行的行为案例，不是已通过的测试：

- “比较两种取消状态归属，给出建议，不修改代码”：`software-design` 交付推荐方案、取舍和必要边界，不只列 findings，不擅自实现，也不默认追加专项评审。
- “检查这份取消方案，只做 review”：`design-review` 交付有证据的问题、检查范围和局限；无问题可以直接说明，不自动重写方案或修改代码。
- “检查方案并给出修订方案，不实现”：在已有授权内交付审查结论与修订方案，不因技能切换要求用户再说“继续”，也不进入实现。
- 已授权实现时遇到未决结构选择：结论足以支持当前工作后继续实现和验证，不把设计文档或专项评审变成新的审批关卡。

## 连续任务测试

结构案例不要只跑单次请求。选择一个有真实历史的小模块，以同一顺序连续完成几项实际需求，每次保留上一步产物，再检查最终的规则分布、职责、依赖与测试难度。预先定义需要保持的行为和契约，不预先规定最终必须长成几个类。

## 调用与安装检查

在实际 Codex 中检查两个 grill 包装入口和 implement 的显式调用；普通实现、对 Spec 的讨论和对 skill 的解释不应意外变成访谈。再验证用户明确要求需求访谈时，grilling 能充分探索并正确交接到文档和开发。

`allow_implicit_invocation: false` 是调用策略，不是权限隔离；授权边界还需宿主环境和工具执行层落实。

## 保留规则的依据

规则带来稳定收益才保留；只对一个项目有效就下移，旧模型补丁无收益就删除。新失败先留下输入、版本、结果和证据，不立即追加全局约束。
