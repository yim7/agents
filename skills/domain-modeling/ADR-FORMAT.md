# ADR 格式

ADR 放在 `docs/adr/` 中，按顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

`docs/adr/` 目录按需创建：只在需要第一份 ADR 时才创建。

## 模板

```md
# {决定的简短标题}

{1～3 句话：背景是什么，决定了什么，为什么。}
```

就这些。一份 ADR 可以只有一段话。它的价值在于记录**做过**这个决定以及**为什么**，而不是把各个章节填满。

## 可选章节

只在确实有价值时加入。大多数 ADR 都不需要。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决定会被重新讨论时有用
- **考虑过的方案**：只在被否决的方案值得记住时
- **后果**：只在需要指出不明显的下游影响时

## 编号

扫描 `docs/adr/` 中最大的编号，然后加一。

## 何时提议 ADR

以下三条必须同时成立：

1. **难以逆转**：以后改变主意的代价可观
2. **缺少背景会令人意外**：未来的读者看到代码会疑惑“他们到底为什么要这样做？”
3. **真实取舍的结果**：确实存在其他方案，而你出于具体理由选择了其中一个

如果一个决定很容易逆转，就跳过：反正可以直接改回来。如果它并不令人意外，就不会有人疑惑为什么。如果没有真正的替代方案，除了“我们做了显而易见的事”之外也没什么可记录的。

### 哪些值得记录

- **架构形态。**“我们使用 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。**“订购和计费通过领域事件通信，而不是同步 HTTP。”
- **带来锁定的技术选择。** 数据库、消息总线、认证服务、部署目标。不是每个库都算：只算那些需要一个季度才能换掉的。
- **边界与范围决定。**“客户数据归客户上下文所有；其他上下文只通过 ID 引用它。”明确的“不做”和“做”一样有价值。
- **刻意偏离显而易见的做法。**“我们用手写 SQL 而不是 ORM，原因是 X。”任何一个理性的读者会默认相反做法的地方。这类记录能阻止下一个工程师去“修复”本来就是刻意为之的东西。
- **代码中看不到的约束。**“出于合规要求，我们不能使用 AWS。”“因为合作方 API 的契约，响应时间必须低于 200ms。”
- **否决理由不明显的备选方案。** 如果你考虑过 GraphQL，但出于微妙的原因选择了 REST，就记下来；否则半年后还会有人再提议 GraphQL。
