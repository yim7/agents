# ADR 格式

架构决策记录（ADR）放在 `docs/adr/` 中，按顺序编号：`0001-slug.md`、`0002-slug.md` 等。

需要第一份 ADR 时才创建该目录。

## 模板

```md
# {决策的简短标题}

{用 1–3 句话说明背景、决定及理由。}
```

一段文字就可以构成 ADR。重点是记录作出了什么决定以及为什么，不必为了填满章节增加内容。

## 可选内容

只有确有价值时才添加，多数 ADR 不需要：

- **状态**：在 frontmatter 中使用 `proposed | accepted | deprecated | superseded by ADR-NNNN`，适用于重新讨论已有决定时。
- **考虑过的方案**：只记录值得记住的未采纳方案。
- **影响**：只说明不容易察觉的后续影响。

## 编号

查找 `docs/adr/` 中已有的最大编号，加一作为新编号。

## 何时建议记录 ADR

必须同时满足三个条件：

1. **难以撤回**：以后改变决定需要付出明显成本。
2. **缺少背景时难以理解**：后来的读者会疑惑为什么这样做。
3. **经过实际取舍**：存在真实的替代方案，并因具体理由选择了当前方案。

容易撤回的决定不必记录；不需要背景解释的决定不必记录；没有实际替代方案的常规做法也不必记录。

### 适合记录的内容

- **架构形式。** 例如采用单仓库，或写模型使用事件溯源、读模型投影到 Postgres。
- **上下文间的集成方式。** 例如订单与计费通过领域事件通信，不使用同步 HTTP。
- **迁移成本高的技术选择。** 如数据库、消息总线、身份认证服务或部署平台；不包括每一个普通库，只包括替换可能需要数月的选择。
- **边界与范围。** 例如客户上下文拥有客户数据，其他上下文只通过 ID 引用。明确不做什么也值得记录。
- **有意偏离常见做法。** 例如基于具体理由手写 SQL 而不采用 ORM，避免后来的维护者把有意的选择当作问题修改。
- **代码中看不出的约束。** 例如合规要求禁止使用 AWS，或合作方 API 合约要求响应低于 200 毫秒。
- **未采纳方案背后不明显的理由。** 例如在比较 GraphQL 与 REST 后因特定取舍选择 REST，避免以后重复讨论。
