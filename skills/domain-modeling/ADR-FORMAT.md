# ADR 格式

ADR 放在 `docs/adr/`（项目已有设计记录目录时沿用），按顺序编号：`0001-slug.md`、`0002-slug.md`。扫描目录中最大的编号并加一。

## 模板

```md
# {决定的简短标题}

{1～3 句：背景是什么，决定了什么，为什么。}
```

一段话就够。ADR 的价值在于记录**做过**这个决定以及**为什么**，而不是填满章节。

## 可选部分

只在确有价值时加入：

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决定会被重新讨论时使用。被替代的 ADR 保留原文，只更新状态并指向新 ADR。
- **备选方案**：只在被否决的方案值得记住时。
- **后果**：只在下游影响不明显、需要指出时。

## 什么值得记录

- **架构形态**：“使用 monorepo。”“写模型事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成方式**：“订购与计费通过领域事件通信，不走同步 HTTP。”
- **带锁定成本的技术选择**：数据库、消息总线、认证服务、部署目标，即需要一个季度才能替换的那类。
- **边界与范围决定**：“客户数据归客户上下文所有，其他上下文只通过 ID 引用。”明确的“不做”和“做”同样有价值。
- **刻意偏离常规的做法**：“用手写 SQL 而不用 ORM，原因是 X。”防止后来者把刻意的选择当错误“修复”掉。
- **代码里看不出的约束**：合规要求、合作方接口的响应时间要求等。
- **理由不明显的否决**：考虑过 GraphQL 但因细微原因选了 REST，就记下来，否则半年后还会有人再提。
