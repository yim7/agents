# GLOSSARY.md 格式

## 结构

```md
# {上下文名称}

{一两句话说明这个上下文是什么、为什么存在。}

## 术语

**订单（Order）**：
{一两句话描述这个术语}
_避免_：购买、交易

**发票（Invoice）**：
交付后发给客户的付款请求。
_避免_：账单、付款请求

**客户（Customer）**：
下订单的个人或组织。
_避免_：委托人、买家、账户
```

## 规则

- **有主见。** 同一个概念有多个叫法时，选出最好的一个，把其余的列在 `_避免_` 下。
- **定义要紧凑。** 最多一两句。定义它**是什么**，而不是它做什么。
- **只收录本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具模式）即使项目大量使用，也不属于这里。添加术语之前先问：这是本上下文独有的概念，还是通用编程概念？只有前者属于这里。
- **自然形成分组时，用小标题归类。** 如果所有术语都属于同一个紧密的领域，平铺列表即可。

## 单上下文与多上下文仓库

**单上下文（大多数仓库）：** 仓库根目录一个 `GLOSSARY.md`。

**多上下文：** 仓库根目录的 `GLOSSARY-MAP.md` 列出各个上下文、它们的位置以及相互关系：

```md
# Glossary Map

## 上下文

- [订购（Ordering）](./src/ordering/GLOSSARY.md)：接收并跟踪客户订单
- [计费（Billing）](./src/billing/GLOSSARY.md)：生成发票并处理付款
- [履约（Fulfillment）](./src/fulfillment/GLOSSARY.md)：管理仓库拣货和发货

## 关系

- **订购 → 履约**：订购发出 `OrderPlaced` 事件；履约消费它来开始拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费消费它来生成发票
- **订购 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

本技能自行推断适用哪种结构：

- 如果存在 `GLOSSARY-MAP.md`，读取它来找到各个上下文
- 如果只有根目录的 `GLOSSARY.md`，就是单上下文
- 如果两者都不存在，在第一个术语确定时，按需创建根目录的 `GLOSSARY.md`

存在多个上下文时，推断当前话题与哪个上下文相关。如果不清楚，就问用户。
