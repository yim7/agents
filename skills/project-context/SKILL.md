# 项目上下文维护

核实并维护后续工作需要的项目知识，不包办需求访谈、方案设计或开发。只要求检查时，交付问题与建议，不修改文件。

## 依据与范围

先核对本次要维护的内容、已有指令、相关代码和记录。区分已核实的实现事实、用户确认的预期、已接受的决定和未决事项；代码现状不自动等于预期行为，一次做法也不自动成为长期规则。

保留领域澄清能力：发现术语冲突、含义不明或文档与代码不一致时，用具体场景检验并指出分歧。可查明的事实自行核查；需要新业务或架构取舍的，交回当前任务处理，不为写完文档擅自决定，也不自动开启整轮访谈。

修改限于用户要求或已授权任务直接影响的上下文。同步已确认事实不需逐行请示；改变长期规则、范围或权限不能借文档维护自行批准。仅发现文档不够完整，不代表授权全面重写。

## 内容归属

沿用项目现有布局和命名，不强制迁移为下面的文件结构。只读取本次产物需要的参考，不要求创建全部文件：

- 项目 `AGENTS.md`：工作入口、必要命令、已确认约束及详细资料索引。参考 [项目指令](references/project-agents.md)。
- `CONTEXT.md` 或已有领域文档：项目特定术语、概念关系和容易误解的业务语义。参考 [领域上下文](references/domain-context.md)。
- ADR 或已有设计记录：重要决定的背景、取舍和当前状态。参考 [决策记录](references/decision-record.md)。

详细定义与理由保留在各自的主要记录位置，其他入口简要提示并引用；不把全文复制进 `AGENTS.md`。当前任务的 TODO、临时排错记录和未选入范围的设想留在任务或 Spec 中，不默认提升为长期上下文。

## 增量维护与交付

在既有内容上更新，保留用户无关改动。修正有依据的过期描述、合并重复内容、维护引用；替代已有决定时保留其历史状态和替代关系，不把旧决定改写成“从未存在”。仅有分歧时先标明待核实，不覆盖任一方来制造一致。

在访谈中，按调用者已有的记录授权及时保存确认的术语和决定；记录本身不结束访谈，也不反向调用访谈入口。模板按实际内容裁剪，不填造事实、复制全局规则或留下无内容的占位章节。

交付改动位置、重要依据及未决事项。核对引用目标、记录状态，以及声称验证过的命令是否有实际结果；没有运行的检查如实注明。相关上下文已同步后回到原任务，不追加全库整理或确认关卡。
