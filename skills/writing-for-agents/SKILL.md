# 写给模型读的文档

AGENTS.md、CLAUDE.md 和技能的 description 每次会话都会加载，每一句都占模型的注意力。目标是每句都改变模型的做法，没有一句是它本来就会做的。

## 写的时候

- **只写模型不知道或默认不会做的。** 每句问一下：删掉它，模型的做法会变吗？不会变就删整句。规则有来历的，带一句为什么，模型才能判断它什么时候不再成立。
- **能直接查到的不抄。** 命令在 `package.json`，目录能列出来，配置在配置文件里，抄进文档迟早过时。只写查不到的：没写下来的约定、选择的理由、踩过的坑。
- **一个意思只写一处。** 别处需要时写一句“见 X”。
- **说要做什么。** “写一行注释”比“不要写长注释”管用。只有硬性底线才用“不要”，并配上该怎么做。
- **精确易读。** 用有共识的术语（tracer bullet、YAGNI、单一职责），一个词比一句解释更省也更稳；不自造术语，非造不可就当场定义。少用抽象表达，能举具体的文件、命令、现象就举出来。用户要读、要维护这些文件，人读得懂，模型自然也读得懂。

## 放在哪

- 每次都要用的放主文件。只在某种情况下才用的，放进同目录的单独文件，主文件留一句“遇到 X 时读 Y”，X 要写具体。
- 文件变长时先删，删不动再拆。

## 写技能时

- description 写什么时候用，不写功能介绍：用户说什么、在做什么时触发。关键词放前面。
- 只有用户主动输入才用的技能，frontmatter 加 `disable-model-invocation: true`，它的 description 就不常驻上下文。需要模型自己判断何时调用的才保持自动。
- 有先后顺序的步骤，每步写清做到什么程度算完成。“每个调用方都已迁移”比“迁移调用方”更不容易做到一半就停。

## 改完之后

从头到尾把整份文件读一遍，删掉过时的、和别处重复的、写历史经过的句子，再交付。只改了一行也要读，文件就是这样一行行变长的。
