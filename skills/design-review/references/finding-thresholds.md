# Finding 门槛

## 何时报告 Finding

当问题有明确设计成本时报告，例如：

- 未来变化影响面变大
- 维护者认知负担变高
- 隐藏依赖或影响范围不清楚
- 同一份知识跨边界重复
- 接口复杂度不必要
- 新抽象层没有用删除或隐藏复杂度来抵消自身成本
- 结构会鼓励后续继续打补丁
- 修复边界问题时引入了过多概念，使维护者需要记住更多对象、DTO 或协议
- read model 被误提升为事实源、领域对象或内部传递对象

## 通常不要报告 Finding 的情况

不要为以下问题提交正式 finding：

- 没有设计影响的风格偏好
- 不妨碍理解的措辞或格式差异
- 命名争议，除非名称削弱抽象或隐藏行为
- 只是略差但不误导的注释
- “边界更干净”但需要增加更多概念的改动
- 仅仅指出某个职责边界没有同名类或 DTO

## 边界情况

如果问题介于可报和不可报之间，问：

- 这会让未来安全修改明显更难吗？
- 读者会因此错过重要设计约束吗？
- 它是否制造了三种复杂度症状之一？
- 如果修复方案要增加抽象，它是否明确降低净复杂度？
- 最小可行修复是否可以只用模块函数、私有方法或 API 边界契约完成？

如果答案是否定的，不要放进 findings。

## 偏向高信号

宁可给出少量重要 finding，也不要给出一长串低信号评论。目标不是覆盖所有可说之处，而是识别最会增加复杂度的设计选择。
