# 审查范围

## `spec`

重点关注：

- 提出的抽象
- 边界是否清楚
- 知识归属
- 接口形状
- 设计会导向深模块还是浅模块

核心问题：

- 如果照这个 spec 实现，复杂度会被局部化，还是会被扩散？

## `plan`

重点关注：

- 任务拆分是否强化了好的边界
- 实现步骤是否按曳光弹式业务切片形成薄闭环
- plan 是否鼓励战术补丁，而不是结构清晰

核心问题：

- 按这个 plan 执行，会自然得到目标设计和可验证闭环，还是只能通过连续补丁近似它？

## PR 描述或变更总结

重点关注：

- 声称的设计意图是否和实际改动形状一致
- 关键设计决策是否解释得足够清楚，方便 reviewer 判断

核心问题：

- 描述是否暴露了真正的抽象变化，还是把它藏在 feature language 后面？

## 接口文档

重点关注：

- 调用方需要知道什么
- 常见情况的接口是否简单
- 实现细节是否泄漏进接口文档

核心问题：

- 文档是在解释抽象，还是在把内部细节负担推给调用方？

## 注释和 Docstring

重点关注：

- 它们是否澄清非显然设计意图
- 它们是否暴露出抽象太弱
- 它们是否只是在复述代码

核心问题：

- 注释是在补充必要的非显然信息，还是在弥补弱设计？

## 代码和 Diff

重点关注：

- 具体警讯
- 边界违规
- 重复知识
- pass-through layer
- 泄漏的特殊情况
- 非显然行为

核心问题：

- 实现后设计是否仍然局部、可读，还是复杂度已经扩散到多个位置？
