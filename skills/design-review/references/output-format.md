# 输出格式

## Findings 优先

先写 findings，并按严重程度或设计影响排序。

每条 finding 应包括：

- 问题是什么
- 为什么它增加复杂度
- 未来可能造成什么维护成本
- 推荐的改进方向
- 最小可行修复是什么，尤其是能否避免新增类、DTO、service 或 adapter

## 推荐 Finding 形状

使用简洁结构，例如：

1. `[Severity] 简短问题标签`
2. 说明问题是什么。
3. 说明它为什么在这个框架下增加复杂度。
4. 说明它可能造成哪类未来变化或维护成本。
5. 说明哪种重设计方向可以降低问题。

条件补充：如果推荐新增抽象，说明为什么模块函数、私有方法或压平 schema 不够。

## 按 Artifact 类型补充

### `spec` 和 `plan`

说明问题在实现中可能如何显现，例如：

- 拆分职责会让同一份知识泄漏到多个模块
- 接口形状会迫使调用方理解罕见情况
- 任务拆分会鼓励打补丁，而不是干净地建立抽象

### 代码和 diff

把 finding 绑定到已经存在的具体结构，例如：

- 重复解析逻辑
- pass-through layer
- 泄漏的配置细节
- 隐藏语义的泛型容器

## 无 Finding 语句

如果没有有意义的 finding，明确写：

> 在 Design Review 框架下，没有发现明确的设计问题。

不要用泛泛表扬或填充性评论替代。

## 抽象减法

当没有必要作为 finding，但存在明显概念减法机会时，可以在 findings 后增加短小的“可删减建议”：

- 哪些名词只是职责边界，不必实现成同名类。
- 哪些对象可以降级成模块函数。
- 哪些 read model 应只保留在 API 边界。
- 哪些功能切片应改成更薄的端到端闭环。

不要为了凑结构输出这个部分；只有它能降低认知负担时才写。
