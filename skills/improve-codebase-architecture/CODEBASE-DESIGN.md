# 代码库设计

> 来源：上游的 [codebase-design](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/codebase-design/SKILL.md) 技能。这里只有本技能用到它，所以作为参考文件放在这里，不单独安装成自动调用技能。

设计**深模块**：小接口背后有大量行为，放在一个干净的接缝上，可以通过这个接口测试。凡是在设计或重构代码的地方，都使用这套语言和这些原则。目标是给调用方带来杠杆，给维护者带来局部性，给所有人带来可测试性。

## 术语表

严格使用这些术语：不要替换成“组件”“服务”“API”或“边界”。一致的语言正是全部意义所在。

**模块（module）**：任何有接口和实现的东西。刻意不限定规模：一个函数、类、包，或者跨层的一个切片。_避免_：单元、组件、服务。

**接口（interface）**：调用方正确使用这个模块必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、必需的配置和性能特征。_避免_：API、签名（太窄，它们只指类型层面的表面）。

**实现（implementation）**：模块内部的东西，它的代码主体。与**适配器**不同：一个东西可以是适配器很小、实现很大（一个 Postgres 仓储），也可以是适配器很大、实现很小（一个内存中的 fake）。话题是接缝时用“适配器”；其他情况用“实现”。

**深度（depth）**：接口处的杠杆。调用方（或测试）每学会一单位接口，能用上多少行为。大量行为藏在小接口后面的模块是**深**的；接口几乎和实现一样复杂的模块是**浅**的。

**接缝（seam）**（_Michael Feathers_）：一个不用修改该处代码就能改变行为的地方；模块接口所在的**位置**。接缝放在哪里本身就是一个设计决定，与接缝后面放什么是两回事。_避免_：边界（与 DDD 的限界上下文含义重叠）。

**适配器（adapter）**：在接缝处满足某个接口的具体东西。描述的是**角色**（它填哪个槽），而不是实质（里面是什么）。

**杠杆（leverage）**：调用方从深度中得到的东西。每学会一单位接口，能获得更多能力。一份实现在 N 个调用点和 M 个测试中得到回报。

**局部性（locality）**：维护者从深度中得到的东西。修改、bug、知识和验证集中在一个地方，而不是散布在各个调用方。改一处，处处都改好了。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│       深实现        │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 很少的实现（避免）：

```
┌─────────────────────────────────┐
│             大接口              │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  薄实现                         │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 能减少方法数量吗？
- 能简化参数吗？
- 能把更多复杂性藏到里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小的、可 mock、可替换的部件组成；它们只是不属于接口。一个模块既可以有**内部接缝**（实现私有的，供它自己的测试使用），也可以有位于其接口处的**外部接缝**。
- **删除测试。** 想象删掉这个模块。如果复杂性随之消失，它只是个透传。如果复杂性在 N 个调用方那里重新出现，它就物有所值。
- **接口就是测试面。** 调用方和测试跨过同一个接缝。如果你想**越过**接口去测试，这个模块的形状多半不对。
- **一个适配器意味着假想的接缝，两个适配器才意味着真实的接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接收依赖，而不是创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积小。** 方法越少，需要的测试越少。参数越少，测试准备越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，相对于它的**接口**来衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**处，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否决的说法

- **把深度当作实现行数与接口行数之比**（Ousterhout）：会鼓励填充实现。我们改用“深度即杠杆”。
- **把“接口”当作 TypeScript 的 `interface` 关键字或类的公开方法**：太窄：这里的接口包括调用方必须知道的每一个事实。
- **“边界”**：与 DDD 的限界上下文含义重叠。说**接缝**或**接口**。
