# 设计两次

用户想为选定的候选比较几种接口设计时用。出发点是 Ousterhout 的“设计两次”：第一个想到的接口通常不是最好的。

## 1. 写清约束

先给用户写一段说明：

- 新接口必须满足的约束；
- 它依赖什么，每个依赖属于哪一类（见 `SKILL.md` 的依赖分类）；
- 一段示意代码，让约束变具体。这不是方案。

写完给用户看，然后马上做第 2 步，不用等回复。

## 2. 并行设计

派 3 个以上子代理同时设计，每个给一个不同的取向：

- 接口尽量小：最多 1 到 3 个入口，每个入口能做的事尽量多；
- 尽量灵活：支持多种用法和扩展；
- 为最常见的调用方优化：默认用法最简单；
- （依赖里有远程服务或第三方时）围绕接缝设计：生产和测试各一种实现。

每个子代理拿到的说明要包含：涉及文件、现在的耦合情况、依赖分类、项目里的领域叫法。没有子代理工具时，自己依次按这几个取向各设计一版。

每个设计都要给出：

1. 接口：方法、参数、返回值，以及调用顺序、出错方式、前提条件；
2. 调用方怎么用的示例；
3. 接口背后藏了哪些逻辑；
4. 依赖怎么处理，测试时换成什么；
5. 取舍：哪种用法很顺，哪种用法别扭。

## 3. 比较并推荐

逐个展示设计，再放在一起比较：调用方要知道多少、修改会集中在哪里、接缝放在哪。最后给出明确推荐：哪个最好、为什么；几个设计的部分能组合得更好，就给出组合方案。
