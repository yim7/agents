# 加深

如何在考虑依赖的前提下，安全地加深一组浅模块。假定你已掌握 [CODEBASE-DESIGN.md](CODEBASE-DESIGN.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估一个加深候选项时，先给它的依赖分类。分类决定了加深后的模块如何跨接缝测试。

### 1. 进程内

纯计算、内存状态、没有 I/O。总是可以加深：合并这些模块，直接通过新接口测试。不需要适配器。

### 2. 可本地替身

有本地测试替身的依赖（Postgres 用 PGLite，内存文件系统）。如果替身存在，就可以加深。加深后的模块在测试套件中搭配运行中的替身来测试。接缝是内部的；模块的外部接口上没有 port。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自家服务（微服务、内部 API）。在接缝处定义一个 **port**（接口）。深模块拥有逻辑；传输方式作为**适配器**注入。测试用内存适配器，生产用 HTTP/gRPC/队列适配器。

推荐的表述方式：*“在接缝处定义一个 port，生产实现 HTTP 适配器，测试实现内存适配器，这样即使部署跨越网络，逻辑也集中在一个深模块里。”*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入的 port 接收；测试提供一个 mock 适配器。

**浏览器环境是例外。** DOM、Canvas、WebGPU 在 Node 测试里造不出来，也没有像样的本地替身。前端候选项的加深方向只有一个：把逻辑挪出组件和渲染类，放进只依赖数据和窄接口的纯模块，让渲染层薄到不需要测。

## 接缝纪律

- **一个适配器意味着假想的接缝，两个适配器才意味着真实的接缝。** 除非至少有两个适配器是合理的（通常是生产 + 测试），否则不要引入 port。只有一个适配器的接缝只是多绕了一层。
- **内部接缝与外部接缝。** 深模块可以有内部接缝（实现私有的，供它自己的测试使用），也可以有位于接口处的外部接缝。不要仅仅因为测试用到了内部接缝，就把它们通过接口暴露出去。

## 测试策略：替换，而不是叠加

- 一旦在加深后模块的接口上有了测试，旧的针对浅模块的单元测试就成了浪费；删掉它们。
- 在加深后模块的接口上写新测试。**接口就是测试面**。
- 测试通过接口对可观察的结果做断言，而不是内部状态。
- 测试应当能挺过内部重构，因为它们描述的是行为，而不是实现。如果实现一变测试就得跟着变，说明它在越过接口测试。
