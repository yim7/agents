# 改进代码库架构

找出架构上的摩擦，提出**加深机会（deepening opportunities）**：把浅模块变成深模块的重构。目标是可测试性和便于 AI 浏览。

本命令以项目的领域模型为依据，并建立在一套共享的设计词汇之上：

- 读取 [CODEBASE-DESIGN.md](CODEBASE-DESIGN.md)，获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、“接口就是测试面”、“一个适配器 = 假想的接缝，两个 = 真实的接缝”）。每条建议都严格使用这些术语，不要漂移成“组件”“服务”“API”或“边界”。
- `GLOSSARY.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决定。

## 流程

### 1. 探索

**先定范围再扫描：YAGNI。** 加深一个模块的回报，是让以后对它的修改变得更容易，所以要给代码库中最近改动过的部分更多权重。看之前先决定**看哪里**：

- 如果用户指定了方向（一个模块、一个子系统、一个痛点），就按它来，跳过下面的推断。
- 否则，往回看一长段提交历史（`git log --oneline`），找出代码库的热点：反复出现的文件和区域，让这些路径先吸引你的注意力。如果改动很分散、没有明显热点，就扩大范围。

先读项目的领域术语表（`GLOSSARY.md`）和你所涉及区域的 ADR。

然后派一个子代理去走查代码库。不要遵循僵硬的启发式规则；有机地探索，记下你在哪里感到摩擦：

- 哪里为了理解一个概念，需要在许多小模块之间来回跳？
- 哪里的模块是**浅**的，接口几乎和实现一样复杂？
- 哪里为了可测试性抽出了纯函数，但真正的 bug 藏在它们被调用的方式里（没有**局部性**）？
- 哪里紧耦合的模块跨过接缝互相泄漏？
- 代码库的哪些部分没有测试，或者很难通过当前接口测试？

对任何你怀疑是浅模块的东西应用**删除测试**：删掉它，复杂性会集中起来，还是只是挪了个地方？“会集中起来”正是你要找的信号。

### 2. 用 HTML 报告呈现候选项

把一个自包含的 HTML 文件写到操作系统临时目录，这样不会有任何东西落进仓库。临时目录取 `$TMPDIR`，没有时用 `/tmp`（Windows 上用 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉用户绝对路径。

报告用 **CDN 引入的 Tailwind** 做布局和样式，在图、流程、时序能可靠表达结构的地方，用 **CDN 引入的 Mermaid** 画图。把 Mermaid 和手写的 CSS/SVG 图形混合使用：关系是图状的（调用图、依赖、时序）时用 Mermaid；想要更有编辑感的东西（体量图、剖面图、折叠动画）时用手写的 div/SVG。每个候选项都有一张**前后对比图**。要可视化。

每个候选项渲染成一张卡片，包含：

- **文件**：涉及哪些文件／模块
- **问题**：当前架构为什么造成摩擦
- **方案**：用平实的语言描述会改变什么
- **收益**：用局部性和杠杆来解释，以及测试会如何改进
- **前后对比图**：左右并排、手工绘制，展示浅的现状和加深后的样子
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章

报告以**首要推荐**一节结尾：你会先处理哪个候选项，为什么。

**领域用 GLOSSARY.md 的词汇，架构用 CODEBASE-DESIGN.md 的词汇。** 如果 `GLOSSARY.md` 定义了“订单（Order）”，就说“订单接收模块”，而不是“FooBarHandler”，也不是“订单服务”。

**ADR 冲突**：如果某个候选项与已有 ADR 相矛盾，只有当摩擦真实到值得重新审视那份 ADR 时才提出。在卡片中明确标注（例如一个警告提示框：*“与 ADR-0007 矛盾，但值得重新讨论，因为……”*）。不要把 ADR 禁止的每一个理论上的重构都列出来。

完整的 HTML 骨架、图形模式和样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

现在**不要**提出接口。文件写好后，问用户：“你想深入探讨其中哪一项？”

### 3. 拷问循环

用户选定一个候选项后，调用 Skill 工具加载 "grilling"，和用户一起走完决策树：约束、依赖、加深后模块的形状、接缝后面放什么、哪些测试能保留下来。

随着决定成形，副作用当场发生；调用 Skill 工具加载 "domain-modeling"，在过程中保持领域模型最新：

- **用一个 `GLOSSARY.md` 中没有的概念为加深后的模块命名？** 把这个术语加入 `GLOSSARY.md`。文件不存在时按需创建。
- **对话中把一个模糊的术语变精确了？** 当场更新 `GLOSSARY.md`。
- **用户以一个关键理由否决了候选项？** 提议写一份 ADR，措辞为：*“要不要我把这个记成 ADR，免得以后的架构审查再提出同样的建议？”* 只有当未来的探索者确实需要这个理由才能避免重复提出同样建议时才提议；临时性的理由（“现在不值得”）和不言自明的理由就跳过。
- **想为加深后的模块探索不同的接口？** 读取 [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md)，使用其中的并行子代理模式。
