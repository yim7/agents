# 架构体检

找出代码库里改起来、测起来最费劲的地方，提出让以后的修改更集中、测试更自然的重构。

## 判断用的几个概念

报告和讨论里统一用这几个词。

- **深模块与浅模块**（Ousterhout《软件设计的哲学》）：深模块是一个小接口背后有大量逻辑，调用方知道得很少就能用上很多；浅模块的接口几乎和实现一样复杂，大多只是把调用转给别处。重构方向是把浅的变深。这里的“接口”指调用方必须知道的一切：参数和返回值，也包括调用顺序、出错方式、前提条件。
- **接缝**（Feathers《修改代码的艺术》）：不改这处代码就能换掉行为的位置，也就是接口所在的地方。调用方和测试都从接缝进来。只有一种实现的接缝只是多绕一层；至少有两种实现（通常是生产一种、测试一种）才值得设。
- **局部性**：一条规则、一类 bug、一次修改集中在一个模块里，而不是散在各个调用方。改一处，处处生效。
- **假想删除**：想象把一个模块删掉。如果复杂度跟着消失，它只是转手；如果复杂度在多个调用方那里重新冒出来，它值得存在，而且可能值得加深。这是判断该不该合并、该不该加深的主要依据，比看文件长短可靠。

领域概念用项目自己的叫法（从 `CLAUDE.md`、spec、评审记录里找），代码里已有的类名、文件名照用，方便对照。

## 1. 找候选

1. 读项目里记录决定的文档（`CLAUDE.md`、spec、评审记录）。写明已定或“先停在这里”的，不重新争论；摩擦真实到值得重提时，在报告里写明冲突的是哪条决定。
2. 定范围。用户指定了模块或痛点就看那里。否则用 `git log --name-only` 统计最近一段提交里改得最多的文件和目录，从那里开始。改得多也可能只是新功能刚落地，不一定是结构问题，要分辨。
3. 读热点代码，记下这几种迹象：
   - 理解一个概念要在许多小文件之间来回跳；
   - 同一条规则在多处各写一遍：用 `grep` 数出现几处、在几个文件，用 `git log` 看改它时是否总要连带改别处；
   - 为了好测抽出了纯函数，但 bug 出在把它们拼起来的地方；
   - 某块逻辑没有测试，或者只有把整个服务跑起来才测得到。
4. 对每个可疑点做假想删除，留下“删掉后复杂度会散到调用方”的作为候选。

完成标准：每个候选都写明涉及的文件、可核实的证据（出现次数、连带修改次数、行数），以及它属于下面哪一类依赖。

## 依赖分类

依赖的类型决定重构后怎么测：

- **纯内存逻辑**：不读写外部。直接合并，通过新接口测。
- **有本地替身的**：数据库用临时文件或内存库，文件系统用临时目录。测试里跑真实的替身，接口不用为测试改。
- **自己控制的远程服务**：在接缝处定义接口，生产用网络实现，测试用内存实现。
- **第三方服务**（交易所、支付、消息推送）：作为参数传进模块，测试传假的。
- **浏览器环境**（DOM、Canvas、WebGPU）：Node 测试里造不出来。把逻辑挪出组件和渲染代码，放进只依赖数据的普通模块，让渲染层薄到不需要测。

重构后的测试写在新接口上，只断言接口给出的结果，不碰内部状态，这样内部再改也不用动测试。原来针对零散小模块的测试被新测试覆盖后删掉。

## 2. 出报告

写一个自包含的 HTML 文件到系统临时目录（`$TMPDIR`，没有就用 `/tmp`），文件名 `architecture-review-<时间>.html`，不放进仓库。格式见 [HTML-REPORT.md](HTML-REPORT.md)。

每个候选一张卡片：涉及文件、问题、方案、好处、前后对比图、依赖类别、推荐程度（强烈 / 值得探索 / 存疑）。推荐程度按证据强弱和收益大小定。对比图里可以写出新模块的方法名，签名和实现留到讨论时再定。报告最后一节写最先做哪一个、为什么。

完成标准：在浏览器里打开过一次，样式生效、每张图都渲染出来、控制台没有报错。然后把文件路径告诉用户，问用户想先深入哪一项。

## 3. 逐项讨论

用户选定一项后，一轮一轮和用户定下：约束、依赖怎么处理、新模块的接口什么样、哪些现有测试能留。每轮只问当前能定的问题，每个问题附上你推荐的答案。

- 用户想比较几种不同的接口设计：读 [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md)。
- 用户以一个关键理由否决了某个候选，而且这个理由下次审查时还用得上：提议在项目 spec 或 `CLAUDE.md` 的对应条目旁记一句“不做 X，因为 Y”。
