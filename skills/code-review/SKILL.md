# 代码变更审查

主要产物是可定位、可解释的缺陷与检查结论。检查具体改动是否正确且完整，不把另一种设计偏好当作返工理由；仅有抽象方案的结构讨论属于设计审查。

## 固定范围与依据

从请求、PR 元数据或当前工作区确定审查对象并固定提交。已有信息足够时不重复询问；范围确有歧义且会改变结论时再澄清。记录比较基点、目标版本和是否包含未提交修改。

- PR／分支新增改动通常比较共同祖先与目标提交；用户明确要求两个快照差异时比较指定端点，不把所有请求都改成三点比较。
- 工作区审查用 `git status --short` 区分状态，按范围检查 `git diff`、`git diff --cached` 和未跟踪文件；不能只看 HEAD 间差异，也不为获取 diff 擅自暂存文件。单纯 PR 审查不混入无关本地修改。
- 无差异、基点不可解析或内容无法取得时，说明具体限制，不虚构审查结果。读取解释影响所需的调用方与测试，不自动展开全库重设计。

查找当前请求、Spec、关联 issue、项目明确规范与相关实现；可访问的依据自行读取。缺少 Spec 时照常检查可判断的正确性，并注明需求符合性无法完全核验，不要求安装 tracker 或启动需求访谈。规格与实现不一致时先核对已接受的变更，不将旧规格自动视为永远正确。

## 检查与复核

同时关注需求遗漏／非预期行为、边界和错误路径、状态／资源处理、兼容与测试覆盖，以及有实际影响的项目规范或结构风险。缺陷可能不在规格里明写；不能因“需求没提”忽略可证明的错误。

代码异味只是线索，不是硬性违规或预设修复方式。重复、类数、层数或某种模式本身不构成 finding；说明具体触发条件与后果，区分本次引入的问题、直接影响本次目标的既有问题和无关改进。

是否并行及视角数量由规模和风险决定，不固定双代理。委派时交接同一范围和原始依据；汇总前回查每个候选发现，合并共同根因，不能将子代理结论原样当作事实。不同视角作为依据标签，不妨碍按实际影响统一排序。

在授权与环境允许时运行有助于验证的检查；工具已覆盖且有可靠结果的风格问题不重复报告，失败检查也不能略过。未运行的检查、无法复现的风险和已证实的缺陷分开说明，不为验证动用未授权环境或修改业务实现。

## 交付

先报告明确问题，每项包含位置、依据或触发条件、后果，以及与影响相称的修复方向；说明哪些需要本次处理。证据不足的疑点与可选建议分开，没有明确问题就如实说明，不凑条数。

补充实际覆盖范围、使用的需求／规范来源、已运行检查与重要未验证部分。未执行的测试不称通过；“没有发现”不是正确性保证，也不是全面安全认证。

只要求 review 时不修改、不发布审查到远程、不批准或合并。用户另有明确修复／发布授权时在原范围内执行，不因技能切换增加确认关卡；不自动调用其他技能形成评审循环。
