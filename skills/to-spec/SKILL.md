本技能基于当前对话上下文和对代码库的理解产出一份 spec。**不要**访谈用户；只综合你已经知道的内容。

spec 以本地 Markdown 保存：`.scratch/<feature-slug>/spec.md`。

## 流程

1. 如果还没有探索过仓库，先探索，了解代码库的现状。整份 spec 都使用项目领域术语表中的词汇，并遵守你所涉及区域的 ADR。

2. 勾勒出你打算在哪些接缝（seam）上测试这个功能。优先使用已有的接缝，而不是新建。使用尽可能高层的接缝。如果需要新接缝，在尽可能高的位置提出。整个代码库中的接缝越少越好，理想数量是一个。

和用户确认这些接缝符合他们的预期。

3. 按下面的模板写 spec，保存到 `.scratch/<feature-slug>/spec.md`（目录不存在时创建）。

<spec-template>

## 问题陈述

用户面临的问题，从用户视角描述。

## 解决方案

问题的解决方案，从用户视角描述。

## 用户故事

一份**很长**的、编号的用户故事列表。每条用户故事使用以下格式：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行客户，我想要查看各账户的余额，以便对自己的支出做出更明智的决定
</user-story-example>

这份用户故事列表应当极其详尽，覆盖这个功能的方方面面。

## 实现决定

已经做出的实现决定列表。可以包括：

- 要新建或修改的模块
- 这些模块中要修改的接口
- 开发者给出的技术澄清
- 架构决定
- schema 变更
- API 契约
- 具体的交互

**不要**写具体的文件路径或代码片段。它们可能很快就会过时。

例外：如果某个原型产出的片段比文字更精确地表达了一个决定（状态机、reducer、schema、类型结构），就把它内联到相关决定中，并简要注明来自原型。只截取承载决定的部分，不是一个能跑的演示，只要关键部分。

## 测试决定

已经做出的测试决定列表。包括：

- 什么是好的测试（只测试外部行为，不测试实现细节）
- 哪些模块会被测试
- 测试的先例（即代码库中类似的测试）

## 不在范围内

本 spec 不包含的内容。

## 补充说明

关于这个功能的其他补充说明。

</spec-template>
