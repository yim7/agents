# 整理规格

产物是本次工作的 Spec，不是长期项目指令或任务拆分。普通小修改无需为了流程生成规格。

## 核对已有结论

读取当前讨论、相关实现和已有规格，沿用已确认术语与决定。区分用户接受的要求、实现现状、候选建议和未决问题；不能把讨论过的全部内容都写成本次承诺。

可查明的事实自行核查。缺失信息不靠填模板补造；非阻断未知保留为未决项。影响规格成立的实质取舍集中提出，并先整理其余已确认内容，不重启逐题访谈或默认增加测试边界审批。

## 形成当前规格

沿用已有文档和格式；没有格式时，按需参考 [规格结构](references/spec.md)。篇幅与任务规模相称，不凑用户故事、章节或备选方案数量。

写清本次目标、预期行为、范围、必要约束和可观察的验收结果。仅记录已决定的实现及验证取舍，不提前规定无依据的类、模块、测试数量或唯一测试层次。关键未知影响实现时，明确其影响和待决定内容，不能把该部分标成已就绪。

已有领域文档、ADR、接口或原型提供定义与依据时，使用准确引用；确有定位价值的路径、提交与代码片段可以保留，但不复制整份资料。未来需求与本次范围分开；本技能不自动更新项目 AGENTS 或生成任务清单。

## 写入与交付

优先更新用户指定或项目已有的规格位置。没有约定时使用 `.scratch/<topic>/spec.md`，核对现有文件与版本控制状态，不覆盖无关内容，也不默认提交。用户只要讨论中的草稿时直接返回草稿，不强制落盘。

本地规格不依赖上游 setup 或 tracker 配置。仅在用户要求发布且目标、内容与权限明确时写入远程；沿用项目已有方式，不自动添加“已批准／可实现”标签。缺少发布条件时交付本地结果并说明缺口。

交付位置、当前范围和重要未决项。已有开发授权时继续原任务；只要求规格时到此结束，不把文档产出视为新授权。
