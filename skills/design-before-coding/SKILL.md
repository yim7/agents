# 编码前设计

## 职责与介入时机

只解决尚未明确的软件结构问题，以清楚的职责、简单的接口和信息隐藏降低复杂度。

- Spec 或任务拆分期间：解决影响整体方案、真实依赖或数据归属的结构问题。
- 当前切片实现期间：只补齐该切片必需的局部设计，不提前设计全部未来功能。
- 先查阅已有 Spec、ADR 和代码。设计已明确时直接沿用；只有新证据表明原决定不适用时才重新评估，并说明原因。

本技能不是固定阶段或审批关卡。不负责需求访谈、UI/视觉设计、完整 Spec 编写、交付排期和曳光弹任务拆分；没有未决结构问题的修改无需启动。

## 需要明确的内容

只回答当前结构问题涉及的内容：

- 哪个模块拥有相关知识、状态和持久化事实。
- 调用方需要什么接口，哪些复杂度应隐藏在模块内部。
- 边界情况如何处理，哪些错误可由接口设计消除。
- 新概念是职责边界、模块、API 契约还是运行时对象；为什么现有模块或聚焦方法不足以承载。

先自行阅读和比较方案。普通技术细节自行决定；只有改变已确认产品行为或涉及用户取舍时，才集中提出必要问题，并继续不受影响的工作。

## 抽象与概念预算

新抽象不是天然更好。每个抽象都会增加名字、概念、接口和维护成本。

引入新类型、层、服务、DTO、adapter 或 protocol 前，先证明它降低了净复杂度。默认先尝试：

1. 删除不必要的代码或概念。
2. 缩小可见性，或把行为移动到当前 owner。
3. 在现有抽象上增加一个聚焦方法。
4. 只有当前几种方式无法隐藏正确知识时，才引入新抽象。

新抽象只有在明显满足至少一项时才值得引入：

- 删除的复杂度多于新增的复杂度
- 用更小的接口隐藏不稳定的设计决策
- 缩小公共接口或防止信息泄漏
- 移除重复特殊情况或成对协议
- 让一个可能的未来变化影响更少位置

不要因为“边界看起来更干净”、某个概念值得命名，或风格偏好而引入抽象。如果新抽象主要是在包一层并转发状态，要把它当作可疑信号。

引入新名词时标注它处于哪一层，避免职责边界被误实现成对象：

- 职责边界：说明谁拥有知识，不自动变成代码对象。
- 模块或文件：把相关知识放在一个地方。
- API 契约：只存在于边界响应或请求中，不作为业务内部对象。
- 运行时对象：封装状态和行为，必须证明比模块函数更清楚。
- 持久化事实源：拥有可恢复事实，不能只是读模型或展示模型。

如果方案突然出现大量新名词，先做概念减法：合并、延后、压平读模型，或把对象降级成模块函数。设计质量包含“未来维护者能一口气理解”。

## 设计过程

1. 先读足够的现有代码或文档，理解当前抽象、边界和职责。
2. 加载 `references/core-principles.md`。
3. 找出主导的复杂度信号：`change amplification`、`cognitive load` 或 `unknown unknowns`。
4. 加载 `references/design-questions.md`，只回答和当前任务有关的问题。
5. 在备选方案里包含最小基线：删除、缩小可见性，或不引入新抽象。
6. 存在实际取舍时比较合理方向，再选定一个；不要为满足数量而虚构备选方案。
7. 比较时关注：
   - 接口是否更简单
   - 信息隐藏是否更好
   - 未来修改成本是否更低
   - 特殊情况和错误是否被内部吸收
   - 概念数量是否真的减少
8. 做概念预算复核：
   - 哪些名字只是职责边界，不会实现成类或 DTO
   - 哪些新对象确实值得新增概念成本
   - 是否可以用更薄的模块函数或 API schema 达到同样效果
   - 是否存在 read model 被误提升成事实源或领域对象
9. 明确写出最终设计决策：
   - 模块归属
   - 接口形状
   - 被隐藏的设计决策
   - 被下沉的复杂度
   - 被设计掉的错误或特殊情况
   - 为什么新增概念值得保留
10. 将结论写回当前 Spec、ticket 或已有设计记录，回到调用本技能的工作；不另建重复规格，不扩大阶段授权。

如果设计仍然难以命名、难以描述，或无法简短解释，加载 `references/design-workflow.md` 继续收敛。

## 最小设计记录

只记录新增或修订的设计决定，已有决定引用即可。小问题一段话即可；复杂问题用短列表覆盖：

- 主导复杂度信号
- 选择的 ownership 边界
- 概念预算：哪些是职责边界，哪些才是需要实现的对象或契约
- 调用方面对的接口
- 被隐藏或移除的复杂度
- 考虑过的最小基线，以及为什么不够

## 与其他技能的交接

- `to-spec` 负责完整规格；本技能补充其中尚未解决的结构决定。
- `to-tickets` 负责曳光弹切片、交付顺序和验收入口；本技能只提供影响拆分的结构约束，不维护另一份执行计划。
- `implement` 负责当前切片的实现和验证；相关设计已足够清楚时退出本技能，继续已授权工作，不新增确认关卡。

## 警讯

以下信号用于定位当前结构问题，不自动触发整套重设计：

- `shallow module`
- `information leakage`
- `temporal decomposition`
- `overexposure`
- `over-abstraction`
- `pass-through method`
- `speculative abstraction`
- `special-general mixture`
- `nonobvious code`
- `concept explosion`
- `read-model-as-source-of-truth`
- `responsibility-boundary-turned-class`

出现这些信号时加载 `references/red-flags.md`。

## 设计偏好

- 偏好简单接口，而不是简单实现。
- 偏好深模块，而不是许多浅包装。
- 按知识边界分配 owner，而不是按执行顺序拆分。
- 把复杂度吸收到模块内部，而不是推给调用方。
- 在引入 DTO 或新层之前，先考虑删除、私有字段和聚焦方法。
- 在信息隐藏相同的前提下，选择概念更少的设计。
- 偏好容易阅读、解释和扩展的设计。
