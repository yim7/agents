# 设计问题

按需使用下面的问题，不必每个任务都回答全部。

## 问题框定

- 这里真正的设计决策是什么？
- 有什么新知识正在进入系统？
- 这是新抽象问题，还是只是局部实现细节？

## 归属和边界

- 哪个模块应该拥有这份知识？
- 哪个模块应该吸收这份复杂度？
- 职责是按知识边界分组，还是只是按执行顺序拆开？
- 如果两个模块都需要同一份设计知识，它们是否应该合并或重新设计？

## 接口质量

- 覆盖常见情况的最简单接口是什么？
- 接口是否迫使调用方理解罕见情况？
- 接口复杂度是否超过了实现收益？
- 是否可以用更深的模块隐藏更多逻辑？

## 抽象价值

- 新抽象移除了什么复杂度，而不是只把复杂度搬到别处？
- 因为这个抽象，哪些代码、概念、公共字段或特殊情况会消失？
- 是否可以通过删除代码、缩小可见性，或在当前 owner 上加一个聚焦方法达到同样效果？
- 这个抽象未来是否足以抵消它新增的名字、类型和接口成本？
- 它减少了净概念数量，还是只是让系统看起来更正式但更难读？
- 这个抽象来自真实重复压力，还是来自 speculative future need？

## 特殊情况和错误

- 哪些特殊情况现在暴露给了调用方？
- 哪些特殊情况可以在内部处理？
- API 是否可以被定义成让这个情况不再是错误？
- 我们是不是因为 API 别扭而增加了异常处理负担？

## 分层

- 每一层是否引入了不同抽象？
- 是否有某层只是原样传递同一组概念？
- wrapper 是否提供了真实价值，还是只增加了间接性？

## 可读性

- 这个抽象容易命名吗？
- 容易简短描述吗？
- 未来读者能快速理解它的责任吗？
- 如果行为不明显，是接口太弱，命名太弱，还是缺少必要文档？

## 未来变化

- 如果这个设计正确，哪类未来变化会更容易？
- 如果这个设计错误，哪类未来变化会更困难？
- 这个设计是在减少后续修改影响，还是在扩散影响？
