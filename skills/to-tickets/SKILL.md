# 拆分交付任务

沿用已确认的目标、范围、设计与现有任务；先核对相关材料，不从标题猜测需求。

## 拆分依据

围绕可验收的结果组织工作。多步产品开发优先曳光弹式迭代，尽早形成一条真实可运行路径；库修复、迁移、调查等按各自的验证结果安排，不要求每项都是新用户功能。

根据实际依赖、可验证性和执行上下文选择粒度，不机械按技术层拆分，也不把拆分结果变成逐步审批。小任务可直接完成，不另建清单。仅声明真正阻塞工作的依赖。

迁移可分为增加兼容形式、迁移调用方、退出旧形式。说明过渡期间的兼容与事实归属、各阶段验证及退出条件；无法安全共存的部分协调修改。需要整合后才能验收时明确整合任务，不把局部通过说成整体可用。

新信息影响当前目标或依赖时更新相关任务；未来设想保留为后续事项，不自动提升成当前交付的前置条件。

## 记录方式

沿用项目已有任务系统和用户的写入授权。没有配置时，在 `.scratch/<feature-slug>/issues/` 中每个任务一个 Markdown 文件，使用稳定编号；后续调整依赖不必重新编号。

最小内容如下，已有任务格式优先：

```markdown
# 01 — 任务标题

## 交付目标

本任务交付什么；必要时说明不包含什么。

## 上下文与约束

相关入口、已确认决定或引用。没有新增信息时可省略。

## 验收条件

- [ ] 可观察、可验证的完成条件。

## 阻塞依赖

真正阻止开工的任务或接口；没有则写“无”。
```

必要设计与规格用引用连接，不复制成长篇任务说明。没有远程写入授权时先交付本地草稿；不因拆分就关闭已有父任务。

只要求拆分时，交付任务清单即结束。已有开发授权时继续可推进的工作，需要持续跟踪时使用同级 [deliver](../deliver/SKILL.md)；不要求用户为每个任务再回复“继续”。
