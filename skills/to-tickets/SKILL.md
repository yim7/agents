# 拆分任务

把计划、spec 或对话拆成一组**任务**：tracer bullet 式的纵向切片，每个任务声明**阻塞**它的其他任务。

任务以本地 Markdown 保存在 `.scratch/<feature-slug>/issues/` 下。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容工作。如果用户传入了引用（spec 路径或任务编号）作为参数，读取它的完整正文和评论。

### 2. 探索代码库（可选）

如果还没有探索过代码库，先探索，了解代码的现状。任务标题和描述应使用项目领域术语表中的词汇，并遵守你所涉及区域的 ADR。

寻找可以先做预重构、让实现变得更容易的机会。“先让改动变容易，再做这个容易的改动。”

### 3. 起草纵向切片

把工作拆成 **tracer bullet** 任务。

<vertical-slice-rules>

- 每个切片切出一条窄但**完整**的路径，贯穿每一层（schema、API、UI、测试）：是纵向切片，**不是**某一层的横向切片
- 完成的切片能够独立演示或验证
- 每个切片的大小能在一个全新的上下文窗口内完成
- 任何预重构都先做

</vertical-slice-rules>

给每个任务标出它的**阻塞边**：开始它之前必须完成的其他任务。没有阻塞的任务可以立即开始。

**大范围重构是纵向切片的例外。** **大范围重构**是一个机械性改动（重命名一个列、修改一个共享符号的类型），它的**影响半径**扩散到整个代码库，一次编辑就会同时破坏成千上万个调用点，没有任何纵向切片能保持通过。不要硬塞成 tracer bullet；按 **expand–contract** 排序。先 expand：在旧形式旁边加上新形式，这样什么都不会坏。然后按影响半径分批（按包、按目录）把调用点迁移过去，每一批是一个独立任务，被 expand 阻塞；因为旧形式仍然存在，每批之间 CI 都保持通过。最后 contract：在没有调用方之后删除旧形式，这个任务被所有迁移批次阻塞。如果连单个批次都无法单独保持通过，仍保留这个顺序，但让它们共享一个整合分支，并且全部阻塞一个最终的整合验证任务；只在那里承诺通过。

### 4. 向用户确认

把拆分方案以编号列表呈现。每个任务展示：

- **标题**：简短的描述性名称
- **被阻塞于**：哪些其他任务（如果有）必须先完成
- **交付内容**：这个任务让哪个端到端行为可用

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确：每个任务是否只依赖真正卡住它的任务？
- 有没有任务应该合并或进一步拆分？

反复调整，直到用户认可这个拆分。

### 5. 写入任务文件

写入认可后的任务：在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每个任务一个文件，按依赖顺序从 `01` 开始编号（阻塞者在前）。每个文件的“被阻塞于”列出它依赖的编号或标题。使用下面的单任务文件模板：一个文件一个任务，绝不合并成一个文件。

推进 **frontier**：所有阻塞者都已完成的任务。对于纯线性的链，就是从上到下。

**不要**关闭或修改任何父任务。

<local-ticket-template>

# <NN>：<任务标题>

**要构建什么：** 这个任务让哪个端到端行为可用，从用户视角描述，而不是逐层的实现清单。

**被阻塞于：** 卡住这个任务的任务编号或标题，或“无（可立即开始）”。

**状态：** ready-for-agent

- [ ] 验收条件 1
- [ ] 验收条件 2

</local-ticket-template>

避免写具体的文件路径或代码片段：它们很快就会过时。例外：如果某个原型产出的片段比文字更精确地表达了一个决定（状态机、reducer、schema、类型结构），就把它内联进去，并简要注明来自原型。只截取承载决定的部分，不是一个能跑的演示，只要关键部分。
