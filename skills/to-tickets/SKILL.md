# 拆分交付任务

基于已有讨论、Spec 和代码理解进行拆分，沿用已确认的术语、设计与范围。用户提供引用时，先核对相关正文和决定；已有拆分只补必要调整。

## 切片与依赖

- 每个任务交付一个窄而完整的可观察行为，贯通它实际涉及的各层，完成后可独立演示或验证。
- 任务大小以一个执行者能在有限上下文内完成为宜；不要把表结构、API、界面分别当作业务交付。
- 只声明真正阻止开工的依赖；依赖未完成的任务不能因追求并行而抢先实现。
- 优先复用现有实现。只有当前交付确实需要时才安排前置整理，不把预备重构当作固定阶段。

跨代码库的机械迁移可按“增加兼容形式 → 分批迁移调用方 → 删除旧形式”拆分，不强求每批都有新用户功能。若只能在合并后运行，应明确共同的整合验收任务，不把各批局部完成称为可用交付。

## 确认与记录

展示任务标题、交付行为、验收条件和阻塞依赖。沿用已确认的粒度与范围；需要用户决定的取舍集中说明原因和建议，常规拆分自行完成，不逐题等待确认。

沿项目已有任务系统记录。没有配置时使用本地文件，不要求先安装其他技能或配置远程系统：

- 本地：在 `.scratch/<feature-slug>/issues/` 下按依赖顺序编号，每个任务一个文件。
- 远程：沿用已有授权和项目约定创建任务，优先使用原生阻塞关系；缺少远程写入授权时先交付本地草稿。已有标签约定直接沿用。

任务至少包含：

```markdown
# 01 — 任务标题

## 交付行为

用户能完成什么，以及会看到什么结果。

## 验收条件

- [ ] 可观察、可验证的完成条件。

## 阻塞依赖

任务编号或链接；没有则写“无”。
```

已有父任务只引用，不因拆分就自动关闭。保持任务说明聚焦交付行为，必要时链接既有设计或接口，避免复制长篇实现细节。

## 交给 deliver

拆分完成不等于开始实现。用户已授权开发时，使用同级目录中的 [deliver](../deliver/SKILL.md) 推进依赖已满足的任务；只要求拆分时交付任务清单。

独立的新任务交接目标、必要约束、接口与验证入口，不机械复制整段会话，也不为每个小修改重新开代理。执行、协作、评审和可用交付统一由 `deliver` 负责。
